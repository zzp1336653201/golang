📖 什么是 Migration？

💡 一句话理解

Migration = 数据库的 Git

就像 Git 记录代码的每次变更一样，Migration 记录数据库结构的每次变更。

类比：Migration vs Git

Git（代码） Migration（数据库）
git commit 创建 migration 文件
git push 提交 migration 到仓库
git pull 拉取 migration 文件
git checkout 执行 down.sql（回滚）
git log 查看 migration 历史
git revert 撤销某个 migration

Migration 文件结构

migrations/
├── 000001_create_users.up.sql -- 创建用户表
├── 000001_create_users.down.sql -- 删除用户表
├── 000002_add_status.up.sql -- 添加状态字段
└── 000002_add_status.down.sql -- 删除状态字段

🔄 up.sql vs down.sql

up.sql：升级数据库（执行变更）

down.sql：降级数据库（撤销变更）

每个 migration 都有两个文件，一个向前，一个向后。

❓ 为什么需要 Migration？

❌ 不用 Migration 的问题

  • 不知道谁改了表
  • 不知道什么时候改的
  • 无法回滚到之前版本
  • 多人改表冲突
  • 测试环境和生产不一致
  • AutoMigrate 可能丢数据

✅ 使用 Migration 的好处

  • 完整的变更历史
  • 随时可以回滚
  • 团队成员同步表结构
  • 环境一致性强
  • DBA 审核后可执行
  • 数据库版本可控

实际案例：多人开发的灾难

1 小明开发

小明在本地添加了 email_verified 字段，测试通过。

2 小红开发

小红在本地添加了 last_login 字段，测试通过。

3 合并代码

两人合并代码，都提交了。没有 migration 记录！

4 部署到生产

😱 生产环境谁的字段都没有！因为没人记得创建这两个字段。

⚠️ AutoMigrate 的危险

如果开着 AutoMigrate，部署时可能：

  • 自动删除了不该删的字段
  • 修改了字段类型导致数据丢失
  • 意外的表结构变化

结论：生产环境必须关闭 AutoMigrate！

⚙️ Migration 工作原理

执行流程

1. 创建 Migration
→
2. 执行 up.sql
→
3. 记录版本
→
4. 完成

版本记录表

Migration 工具会创建一个表来记录执行状态：

-- golang-migrate 创建的表
CREATE TABLE IF NOT EXISTS schema_migrations (
    version BIGINT NOT NULL PRIMARY KEY,
    dirty BOOLEAN NOT NULL DEFAULT false
);

-- goose 创建的表
CREATE TABLE IF NOT EXISTS goose_db_version (
    id BIGINT NOT NULL PRIMARY KEY,
    version BIGINT NOT NULL UNIQUE,
    applied_at TIMESTAMP NOT NULL,
    description VARCHAR(255) NOT NULL
);

具体示例

000001_create_users.up.sql：

CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_username ON users(username);
CREATE INDEX idx_users_email ON users(email);

000001_create_users.down.sql：

DROP TABLE IF EXISTS users;

000002_add_status.up.sql：

ALTER TABLE users ADD COLUMN status INTEGER DEFAULT 1;
ALTER TABLE users ADD COLUMN updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP;

000002_add_status.down.sql：

ALTER TABLE users DROP COLUMN status;
ALTER TABLE users DROP COLUMN updated_at;

🛠️ 推荐工具

1. golang-migrate（推荐）

🔧

golang-migrate

最流行的 Go 数据库迁移工具，支持多种数据库

安装：

# macOS
brew install golang-migrate

# Windows (下载二进制)
# https://github.com/golang-migrate/migrate/releases

# 或用 Go 安装
go install -tags 'postgres' github.com/golang-migrate/migrate/v4/cmd/migrate@latest

使用：

# 1. 创建 migration 文件
migrate create -ext sql -dir migrations -seq create_users_table

# 2. 编辑生成的文件

# 3. 执行升级
migrate -path migrations -database "postgres://user:pass@localhost:5432/db?sslmode=disable" up

# 4. 执行降级（回滚1步）
migrate -path migrations -database "postgres://user:pass@localhost:5432/db?sslmode=disable" down 1

# 5. 查看状态
migrate -path migrations -database "postgres://user:pass@localhost:5432/db?sslmode=disable" version

📋 标准工作流程

开发流程

1 本地开发

在本地开发功能，测试通过。

2 确定表变更

明确需要修改哪些表结构。

3 创建 Migration

使用工具生成 migration 文件。

4 编辑 SQL

编写 up.sql 和 down.sql。

5 提交代码

提交代码和 migration 文件到 Git。

6 CI/CD 或 DBA 执行

在测试/生产环境执行 migration。

7 部署代码

确认 migration 执行成功后，部署应用代码。

✅ 黄金法则

  1. 先 Migration，后部署代码
  2. Migration 和代码必须一起提交
  3. 生产环境由 DBA 执行 Migration
  4. 保留 down.sql，随时可以回滚

🚀 Migration 是什么？

💡 性质说明

Migration 是一个独立的 CLI 工具，不是 Go 依赖、不是插件、不是数据库开关

它是一个单独安装的命令行程序，通过命令执行 SQL 脚本来管理数据库结构

跟 Git 的类比

Git（代码） Migration（数据库）
安装：brew install git 安装：brew install golang-migrate
命令：git commit 命令：创建 migration 文件
命令：git push/pull 命令：提交/拉取 SQL 文件
命令：git checkout 命令：migrate down（回滚）
工作区：代码文件 工作区：SQL 脚本文件

工作原理

1. 你在本地创建 SQL 文件（migrate create）
2. 工具执行 SQL（migrate up）
3. 工具记录版本到数据库（schema_migrations 表）
4. 团队成员拉取后执行相同的命令

🔑 关键点

Migration 工具只是帮助你执行 SQL 脚本，并记录已执行的状态

SQL 脚本本身需要你自己编写，工具不生成 SQL

🛠️ 生产环境使用方法

✅ 推荐方式：独立 CLI 命令

Migration 是一个独立的命令行工具，在部署服务器上直接执行命令

方式一：服务器上手动执行（适合小团队）

# 1. 安装 migrate 工具
curl -L https://github.com/golang-migrate/migrate/releases/download/v4.18.1/migrate.linux-amd64.tar.gz | tar xvz
sudo mv migrate /usr/local/bin/

# 2. 执行升级（执行所有 pending 的 migration）
migrate -path ./migrations -database "postgres://user:pass@localhost:5432/db?sslmode=disable" up

# 3. 查看状态
migrate -path ./migrations -database "postgres://user:pass@localhost:5432/db?sslmode=disable" version

# 4. 回滚（撤销最近的 migration）
migrate -path ./migrations -database "postgres://user:pass@localhost:5432/db?sslmode=disable" down 1

方式二：CI/CD 流水线（推荐，适合生产环境）

# .gitlab-ci.yml 示例
deploy:
  script:
    - migrate -path ./migrations -database $DATABASE_URL up
    - # 然后部署应用

方式三：Go 代码中执行（不推荐生产）

// 仅适合开发环境快速测试
m, _ := migrate.New("file://./migrations", "postgres://...")
m.Up()

📝 常见问题

Q1: 可以不用 Migration 工具吗？

可以！只要你能管理好 SQL 文件就行。但工具提供了：

  • 自动版本控制
  • 防止重复执行
  • 事务支持
  • 回滚功能

Q2: 多人同时创建 migration 怎么办？

使用序列号（seq）来区分：

000001_xxx.up.sql
000002_xxx.up.sql
000003_xxx.up.sql

Git 会自动合并，没有冲突！

Q3: 已经在生产数据库上改过了怎么办？

补创建 migration 文件，标记为已执行即可。

Q4: 如何处理大数据量的表变更？

分步骤执行：

-- Step 1: 添加可空字段
ALTER TABLE users ADD COLUMN phone VARCHAR(20);

-- Step 2: 后台迁移数据
UPDATE users SET phone = old_phone;

-- Step 3: 添加 NOT NULL 约束
ALTER TABLE users ALTER COLUMN phone SET NOT NULL;
