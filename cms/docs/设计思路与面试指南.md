## 一、项目定位

**一句话介绍**：基于 Go + Gin 的企业级电商后端系统，展示了完整的订单流程、库存控制、缓存策略等工程实践。

**求职定位**：

## 二、技术选型

### 为什么用 Gin 而不是其他框架？

| 框架 | 优势 | CMS 选择 Gin 的原因 |
|------|------|---------------------|
| Gin | 性能高、API 简洁、社区活跃 | ✅ 主流选择，企业常用 |
| Echo | 性能更好、零依赖 | 中小型项目两者皆可 |
| GoFrame | 功能完善、适合大型项目 | 学习成本高，中小企业用得少 |
| Hertz | 字节跳动开源 | 主要在字节内部使用 |

**面试回答**：
> "Gin 是目前 Go 生态里最成熟的 Web 框架，社区活跃、文档完善、中间件丰富。像京东、Uber 这些公司都在用。主流招聘要求基本都是熟悉 Gin 开发。"

### 为什么用 GORM 而不是原生 SQL？

**回答**：
> "GORM 适合快速开发，能减少样板代码。对于中小型项目，完全够用。如果追求极致性能，可以裸写 SQL，但开发效率会降低。"

**进阶回答**：
> "我理解 ORM 的原理，知道 N+1 问题，所以在关键查询会用原生 SQL 优化。"

## 三、核心模块设计

### 1. 订单创建流程（最重要）

```
用户下单
    ↓
校验商品和库存
    ↓
扣减库存（分布式锁 + 行锁）
    ↓
创建订单记录
    ↓
创建订单项记录
    ↓
提交事务
    ↓
返回订单号
```

**面试重点**：
- 为什么要用事务？（保证原子性，要么全成功要么全失败）
- 分布式锁解决什么问题？（多实例部署时防止超卖）
- 行锁 `SELECT ... FOR UPDATE` 解决什么问题？（防止并发更新同一行）

---

### 2. 库存扣减（超卖问题）

**问题描述**：
```
两个请求同时下单，都查到库存=1
A请求：库存-1 = 0，下单成功
B请求：库存-1 = -1，下单成功 ← 超卖！
```

**解决方案**：

```go
// 1. 分布式锁（防多实例并发）
locked := redis.SetNX("stock:lock:1", "1", 10*time.Second)
if !locked {
    return errors.New("系统繁忙")
}
defer redis.Del("stock:lock:1")

// 2. 行锁（防同实例内并发）
tx.Set("gorm:query_option", "FOR UPDATE").First(&product, id)

// 3. 库存校验
if product.Stock < quantity {
    return errors.New("库存不足")
}

// 4. 原子扣减
tx.Model(&Product{}).Where("id = ?", id).
    Update("stock", gorm.Expr("stock - ?", quantity))
```

**面试回答**：
> "超卖问题需要双重保障。第一层是分布式锁，保证多台机器同时只有一个请求能操作库存。第二层是数据库行锁 `SELECT FOR UPDATE`，保证同一时刻只有一个事务能修改这条记录。两层锁配合，基本不会出现超卖。"

### 3. 缓存策略（三个经典问题）

#### 缓存穿透

**问题**：恶意请求查询不存在的商品，每次都穿透到数据库

```
请求: GET /products/-1
缓存: 未命中
DB:   SELECT * FROM products WHERE id = -1  ← 每次都查
```

**解决**：空值缓存

```go
if product == nil {
    // 空值也缓存，但时间短一点
    redis.Set(key, "__nil__", 60*time.Second)
}
```

#### 缓存击穿

**问题**：热点 key 突然过期，大量请求同时涌入数据库

```
缓存 key = "product:1"  ← 突然过期
瞬间 1000 个请求同时查 DB ← 数据库被打死
```

**解决**：分布式锁

```go
// 抢锁
locked := redis.SetNX(key+":lock", "1", 10*time.Second)
if !locked {
    // 抢不到就等一下再试，或者直接返回旧数据
    time.Sleep(100*time.Millisecond)
    return redis.Get(key)
}

// 抢到了就去查 DB，然后写入缓存
product := db.First(id)
redis.Set(key, product, 10*time.Minute)
redis.Del(key+":lock")
```

#### 缓存雪崩

**问题**：大量缓存同时过期

```
商品缓存都在 10:00 过期 ← 10:00 大量请求打到 DB
```

**解决**：过期时间加随机值

```go
// 不要写死 10 分钟
ttl := 10*time.Minute + time.Duration(rand.Int63n(60))*time.Second
redis.Set(key, data, ttl)
```

### 4. 限流算法

**令牌桶 vs 滑动窗口 vs 计数器**

| 算法 | 原理 | 特点 |
|------|------|------|
| 计数器 | N 秒内最多 M 次请求 | 最简单，有临界问题 |
| 滑动窗口 | 统计时间窗口内的请求数 | 更精确，实现复杂 |
| 令牌桶 | 按固定速率添加令牌，请求消耗令牌 | 支持突发流量 |

**令牌桶实现**：

```go
type TokenBucket struct {
    rate       int       // 每秒补充的令牌数
    bucket     int       // 桶容量
    tokens     int       // 当前令牌数
    lastUpdate time.Time // 上次更新时间
}

func (tb *TokenBucket) Allow() bool {
    // 1. 补充令牌（基于时间流逝）
    elapsed := time.Since(tb.lastUpdate).Seconds()
    tb.tokens += int(elapsed * float64(tb.rate))
    if tb.tokens > tb.bucket {
        tb.tokens = tb.bucket
    }
    
    // 2. 有令牌就处理
    if tb.tokens > 0 {
        tb.tokens--
        return true
    }
    return false
}
```

**面试回答**：
> "令牌桶的好处是能处理突发流量。比如配置 QPS=100，桶容量=200，那瞬间来 200 个请求也能处理，只要后续请求能匀速进来。我用 Redis 也可以实现分布式限流，生产环境会用 Redis+Lua 脚本保证原子性。"

## 四、面试问题预测

### Q1: 你们项目为什么这样分层？

**参考回答**：
> "标准的洋葱架构，分层职责清晰。Handler 负责接收请求和返回响应，Service 负责业务逻辑，Repository 负责数据访问。这样的好处是职责单一，方便测试。比如要换数据库，只需要改 Repository 层，Service 层不用动。"

### Q2: 如果订单创建失败了，库存会回滚吗？

**参考回答**：
> "会的。整个订单创建过程在一个事务里。如果扣库存成功但创建订单失败，事务会自动回滚。另外我还用了 defer + recover，防止程序 panic 导致事务未关闭。"

### Q3: Redis 挂了怎么办？

**参考回答**：
> "项目里做了降级处理。如果 Redis 连接失败，会打印警告日志，但系统会继续运行（走数据库）。这样保证了可用性，只是性能会下降。另外关键数据（如库存锁）必须依赖 Redis，这种情况会直接返回错误。"

### Q4: 你们项目的并发量大概多少？

**参考回答**：
> "本地测试的话，单机 QPS 大概能到 5000-8000（取决于机器配置）。实际部署会做水平扩展，加上限流保护。"

### Q5: 为什么价格用整数（分）而不是浮点数？

**参考回答**：
> "浮点数有精度问题，比如 0.1 + 0.2 = 0.30000000000000004。金融场景必须避免。用整数（分）存储，计算时手动处理小数点位置，精确又高效。"

## 五、面试表达技巧

### 1. 用数据说话

| 不好的说法 | 好的说法 |
|-----------|---------|
| "性能还行" | "单机 QPS 5000+，P99 延迟 50ms" |
| "做了优化" | "通过缓存 + 索引优化，查询时间从 500ms 降到 20ms" |
| "用户很多" | "峰值日活 10 万，同时在线 5000+" |

### 2. 讲清楚"为什么"

| 不好的说法 | 好的说法 |
|-----------|---------|
| "用了 Redis 缓存" | "因为商品查询是热点读场景，用 Redis 缓存能减少数据库压力，读 QPS 提升 10 倍" |
| "用了事务" | "订单创建涉及库存扣减和订单记录，必须保证原子性，否则会出现付了钱但没生成订单的情况" |

### 3. 主动暴露问题和解决方案

**不要说**：
> "项目很顺利没什么问题"

**要说**：
> "遇到了超卖问题，最开始只用了数据库锁，但部署多实例后发现还是超卖。后来加了分布式锁才解决。"
